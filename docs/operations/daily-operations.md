# Daily studio operations

Open **Daily operations / Дневни операции** in the staff web workspace. In the native app choose **Trainer / staff sign-in / Најава за тренер / персонал**. Staff access is independent from being a studio customer. Select the studio before opening its schedule. Native staff credentials are kept in native secure storage.

Today uses the studio's clock. Choose an inclusive date range up to 31 days. Filters narrow the sessions you already have access to; trainers cannot use them to see someone else's classes. Trainer/location/group choices come from the current page and are labelled accordingly. Pagination does not change the aggregate totals. Cancelled and changed occurrences remain identifiable.

Open **Roster / Список на учесници** to inspect reservations and waiting demand. Search names within the session. Waiting positions follow the studio's existing FIFO queue, not alphabetical display order. Reserved, present, free and waiting are different numbers. Cancelled reservations are retained for context.

Use the attendance controls to mark a booked active member present during the permitted window. After the session ends, record absence or no-show. A correction needs the separate correction permission and an explicit mistake/late-confirmation reason. There is no undo-to-unmarked operation. Opening a roster never finalizes attendance automatically.

For a walk-in, use the existing scoped lookup and admission action. The server enforces active membership identity, timing, capacity and queue priority together. A failed admission must leave no reservation or attendance behind. Present attendance protects reservation cancellation; any recorded attendance protects session edits/cancellation.

If another operator changes the record, refresh and review the returned state. A rejected action is not success. Web attendance also polls every ten seconds; native refreshes on app resume and supports pull-to-refresh. No writes are queued offline. Reauthenticate when access expires, and refresh after assignment/permission changes.

Quick profiles reveal only permitted participation and financial information. Duration plans have dates, not visit counters. A payment warning is separate from membership validity and does not block attendance in the current domain. Restricted or unavailable financial data does not mean paid. Authorized web users follow membership/payment links to the existing finance workspace; finance remains owned by that workflow. Native financial details are informational; follow-up buttons open the existing staff web finance workspace with the organization public ID. Web authentication is separate: sign in and verify the displayed studio before recording/correcting money. Native bearer credentials are never passed to the browser. Permitted web quick profiles also link to the existing full client profile.

Communication counts cover the last 31 days and only appear to authorized studio administrators. Provider status does not prove that a person saw a message. Opening the dashboard sends nothing. Use existing settings/announcement controls for communication work.

MK and EN are available. The web layout supports desktop, tablet and phone; the native screens use large controls, scrolling and native secure credentials. Do not take screenshots containing live QR credentials or real member data for verification.
