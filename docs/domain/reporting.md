# Reporting metric dictionary — GT017.1

GT-017 reads the existing PostgreSQL domains. It does not create financial events, change attendance, allocate places, renew memberships, send notifications or adopt grants. The API, web, native app and exports use `Report` and the same dictionary. Minor money units are exact integers serialized as strings; 100 units = 1 MKD. Rates are rounded to two decimal percentage points only after aggregation.

## Shared population and time contract

Every response is a current, request-local, read-only REPEATABLE READ snapshot with one fixed studio clock. Primary and comparison ranges share that database snapshot. `as_of` identifies request preparation, not a reusable historical snapshot token. Every new request, page and export obtains a fresh snapshot. No report cache or warehouse exists.

The authoritative organization timezone resolves inclusive date filters into `[local midnight from, local midnight after until)`. PostgreSQL groups instants in that IANA zone. Weeks start Monday; daily/weekly/monthly boundaries outside the selected interval produce explicitly `partial` buckets. Empty event buckets are zero. Europe/Skopje DST days can contain 23 or 25 hours; two repeated clock labels represent two different instants. Sessions belong to their start date, without prorating across midnight. Duration membership dates are inclusive local dates. No device timezone changes the population. Existing settings prohibit timezone changes once schedule/session history exists; no historical timezone is invented for financial records predating a permitted setting change.

All reports require authenticated, current `TenantContext`, `studio.access` and `reports.view`. Financial reports also require `payments.view` and deny the Trainer role. Whole-studio activity/expiry require all-location `members.view` plus `memberships.view` and deny Trainer. Operational reports require `sessions.view` and `attendance.view`, with existing current location and Trainer assignment scope from `SessionDirectory`. There is no implicit Super Admin or TrainerProfile grant. Report details never expose notes, contact data or credentials. Operational detail grain is a session, not an identifying member list.

## Financial metrics

| Metric / question                    | Canonical source and grain                                            | Inclusion, time, calculation                                                            | Reconciliation / missing behavior                                                                     |
| ------------------------------------ | --------------------------------------------------------------------- | --------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| `payments`, receipts counted         | `cash_payments`, one posting                                          | Tenant and original `paid_at` in the selected half-open interval; optional sold plan ID | Every posting counted once, including a subsequently reversed posting                                 |
| `gross_minor`, cash recorded         | Immutable cash posting                                                | Sum `amount_minor`                                                                      | Sum of buckets = selected detail rows = independent cash ledger sum                                   |
| `reversed_minor`, corrected receipts | Unique full `payment_reversals` joined on tenant and cash payment     | Sum the original posting's linked reversal amount; original payment period              | Later reversal restates the original period, matching GT-009; it is not a newly dated physical refund |
| `net_minor`, net cash collections    | Same one-posting grain                                                | Gross minus linked full reversals                                                       | Exact gross − reversed = net; no accrual recognition or trainer/group attribution                     |
| Settlement `memberships` / `members` | `member_memberships`, one sold obligation / distinct member           | Current selected population, optional plan, validity state and payment state            | A member with two obligations counts twice only in memberships, once in members                       |
| `agreed_minor`, obligation value     | Immutable sold membership snapshot                                    | Sum agreed prices, including cancelled obligations unless filtered                      | Uses the sold price, never the current plan price                                                     |
| `paid_minor`                         | Cash first aggregated by membership after linked reversal subtraction | Sum net posted cash across all dates for each obligation                                | No session/attendance join can multiply money                                                         |
| `balance_minor`                      | One obligation                                                        | Agreed price − net paid                                                                 | Can be negative (overpayment); not an entitlement balance                                             |
| `outstanding_minor`                  | One obligation                                                        | Sum max(balance, 0)                                                                     | Overpayments do not offset another obligation's unpaid amount                                         |
| `payment_state`                      | Same current obligation                                               | balance < 0: overpaid; = 0: paid; > 0 with paid = 0: unpaid; otherwise partially paid   | Validity is independent of payment settlement                                                         |

GT-009 supports settled cash, idempotent payment requests and one full correction reversal. It does not support pending cash confirmation, provider failures, partial refunds, allocations to groups, accrual revenue, waived obligations, tax, overdue collection rules or multiple currencies. These are unavailable capabilities, not zero-valued invented states. Full reversals cannot exceed their original receipt, so negative **net collections** are not representable in the current ledger; negative settlement balances are supported and tested. Reporting does not edit ledger entries to obtain reconciliation.

Example: 10,000 agreed, receipts 4,000 + 7,000 → net paid 11,000, balance −1,000, overpaid. Retrying the same request ID adds nothing. Reversing the original 4,000 later makes its original receipt period net zero and the membership balance 3,000. The reversal creation date is audit evidence, not a second cash receipt date.

## Current membership and member activity

| Metric                              | Grain / population                         | Definition and time                                                                                                     | Missing/comparison behavior                                                                                         |
| ----------------------------------- | ------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| Activity `members` by `status`      | All tenant StudioMembers                   | Current active/inactive/etc. status as stored                                                                           | This is not status at the selected historical end date                                                              |
| `eligible` / `ineligible`           | Distinct member                            | At least one uncancelled membership with starts_on ≤ studio today ≤ ends_on / its complement                            | Payment settlement does not gate eligibility; eligibility does not mean membership admission is enforced            |
| `participated` / `not_participated` | Distinct member                            | At least one present attendance on a scheduled, ended occurrence starting in the selected interval / its complement     | Future, cancelled, absent, no-show and unresolved records do not count; only participation is historically compared |
| Expiry `memberships` / `members`    | Uncancelled memberships / distinct members | Current expiry buckets: before today; today through +7; +8 through +14; +15 through +30; later                          | Buckets are disjoint, member counts across buckets are non-additive; no historical snapshot comparison              |
| Validity `state`                    | Sold membership                            | cancelled if cancelled_at exists, otherwise upcoming if starts_on > today, expired if ends_on < today, otherwise active | All date ranges shown alongside this remain current snapshots                                                       |

Settlement and expiry intentionally ignore historical date filters for their **current-state** population and say so in UI/metadata. No historical balances, active status or expiry state are reconstructed from today's mutable rows. Existing member/membership workflows remain the authoritative follow-up actions.

## Operational metrics

Session grain is a durable TrainingSession starting in the chosen interval and visible through current staff location/Trainer scope. Group/trainer attribution uses retained session IDs and snapshot labels, not recurring templates or current primary trainers. Historical reassignment versions that were never stored cannot be reconstructed. Reservation and attendance facts are aggregated before joining sessions. Walk-ins use their canonical active reservation and attendance, without an extra reporting category or double count.

| Field                                                            | Population and formula                                                                                      | Denominator / exclusions                                                                                                     |
| ---------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `sessions`, `cancelled`                                          | All scoped occurrences; count cancelled status                                                              | Cancelled occurrences remain identifiable                                                                                    |
| `held`                                                           | Scheduled occurrences whose ends_at ≤ fixed clock                                                           | Future/in-progress and cancelled excluded                                                                                    |
| `capacity`, `reserved`, `waiting`                                | Sum session capacity snapshots, active reservations, current waiting entries for scheduled occurrences      | These are current occurrence states, including future scheduled occurrences; cancelled excluded                              |
| `held_capacity`, `expected`                                      | Capacity and active reservations on held occurrences                                                        | Uses configured occurrence capacity, never group capacity or speculative availability                                        |
| `present`, `absent`, `no_show`, `pending`                        | Active reservations on held occurrences joined to current attendance outcome; missing attendance is pending | Explicit no_show only; passage of time never finalizes absence                                                               |
| `resolved`                                                       | present + absent + no_show                                                                                  | Pending is separately visible and excluded                                                                                   |
| `attendance_rate`                                                | 100 × present / resolved                                                                                    | Not present / all bookings                                                                                                   |
| `no_show_rate`                                                   | 100 × explicit no_show / resolved                                                                           | Unknown is not absence                                                                                                       |
| `occupancy_rate`                                                 | 100 × active reserved / scheduled capacity                                                                  | Weighted aggregate ratio, not average session percentages                                                                    |
| `utilization_rate`                                               | 100 × present / held capacity                                                                               | Actual held usage, not booked occupancy                                                                                      |
| `session_cancellation_rate`                                      | 100 × cancelled / sessions                                                                                  | Occurrence-start population                                                                                                  |
| `reservation_cancelled`                                          | Cancelled reservation records for scoped occurrences                                                        | Current impact by occurrence date, not cancellation event date                                                               |
| `session_cancellation_events`, `reservation_cancellation_events` | Cancellations whose stored cancelled_at falls in the selected interval, independently of occurrence date    | Same tenant/location/trainer scope; separate event-count columns in each date bucket, distinct from occurrence-impact series |
| `unique_participants`                                            | Distinct present StudioMembers on held occurrences                                                          | Deduplicated independently overall and per dimension; dimensions are not additive                                            |

Empty denominators produce JSON null, UI “—”, and empty export cells, never 0% or infinity. Zero numerators with positive denominators produce 0%. Existing PostgreSQL capacity constraints exclude zero/null capacity and canonical allocation excludes over-capacity; reporting does not relax those constraints or clamp hypothetical inconsistent rates.

Attendance, occupancy and cancellations include date series plus group/trainer/local weekday-hour rankings. Popularity ranks by present attendance (default), reserved demand or current waiting demand, with deterministic public-ID ties, top 10 by default / maximum 50 and truncation indicators. Slot keys are ISO weekday 1–7 and local hour 00–23; repeated DST hours share the same slot but occurrences remain distinct. Current waiting entries are demand at snapshot time, not historical waiting demand.

## Comparisons, precision and output

The default UI comparison is the immediately preceding equal number of local calendar days. Custom intervals are separately bounded to 366 inclusive days. Both periods use the same grain and scope. Absolute change is current − previous; relative change is undefined/null for non-positive baselines. Rate differences also provide percentage points. Current settlement/expiry do not offer a false historical comparison; activity compares participation only.

JSON money strings retain exact minor units. CSV stores signed integer money; untrusted text is formula-escaped. XLSX stores money as numeric only within Excel's 15-digit precision; larger values remain exact literal text. Identity/name fields remain literal strings, including numeric-looking labels. Chart lengths are approximate display geometry alongside exact tables, never financial arithmetic. The chart shows at most 60 buckets and labels that limit; the full bounded table remains available. Summary exports contain summary rows; detail exports include every matching detail row within the independent 50,000-row bound, not only the visible page.
