# Studio settings (GT-014)

Studio policies are tenant-owned, explicitly typed configuration. General identity remains on `organizations`; operational overrides live in a single optional `studio_settings` row per organization. `StudioSettings` is the sole resolver: an explicit non-null override wins, otherwise the catalog default applies. No row is necessary and GET never creates one. No key/value storage, arbitrary JSON, Redis dependency or cross-request cache exists. A readonly typed policy object can be reused within a read page; every writer resolves a fresh object after locking its organization.

## Catalog

Every key below accepts JSON null to restore its default. Boolean values must be actual JSON booleans; integers must be JSON integers, not strings, floats or booleans. Empty strings do not reset settings. PATCH bodies are capped at 4 KiB and unknown fields are rejected. PostgreSQL uses nullable boolean/smallint columns, numeric CHECK constraints and a QR overlap CHECK.

The catalog captures actual GT-013 defaults, including the distinction between a 56-day discovery window and previously unrestricted booking of existing future sessions. Bounds limit policy impact to at most one day of booking/cancellation cutoff, two hours around check-in, three days of reminder lead and one month of expiry warning. No settings widen query page sizes or scheduled batch size (maximum 200 per notification type).

## General identity, locale and timezone

The existing organization PATCH remains authoritative for name, MK/EN locale, valid IANA timezone, MKD currency and controlled active/inactive status. No new contact/legal/logo fields are fabricated. Location address/contact ownership remains unchanged. Existing lifecycle checks and grants still apply.

Locale precedence is stored member preference, then organization locale, then application fallback. Existing StudioMember preferred_locale is non-null: preserve it, including preferences originally initialized from the studio. New member creation copies the current organization locale; changing the studio locale does not overwrite existing preferences. The member settings endpoint returns the resolved locale. Translation text stays in MK/EN source catalogs. Staff may independently select their interface language.

A timezone change is rejected once ANY ScheduleRule or TrainingSession exists (including cancelled/history), using the existing application and PostgreSQL protections. The UI explains this and confirms requested changes. Before any schedule/session exists it may change future local calculations, without rewriting timestamps, sold membership dates or prior evidence. More permissive timezone migration is intentionally deferred.

## Authorization, API and audit

- `GET /api/v1/organizations/{organization}/settings`: authenticated TenantContext plus `organizations.view`. Returns effective values, nullable overrides and finite catalog; no internal config or secrets.
- `PATCH` at the same URL: `organizations.manage`, plus the existing staff access/token gates and 30/minute write throttle (also 120/minute API throttle). Same-origin session requests require CSRF; bearer requests require existing staff token authority. TrainerProfile alone grants nothing. Existing grants are not expanded.
- `GET /api/v1/member/organizations/{organization}/settings`: own active MemberContext with member.read; finite subset of self-service flags, booking/check-in windows and resolved locale. No member PATCH route or admin catalog.
- General settings continue through the existing organization GET/PATCH, preserving their explicit authorization and protected-field validation.

Mutations lock Organization and re-resolve active authority before reading the current override row. Only submitted known fields change. Concurrent edits to separate keys merge; same-key edits use last successfully serialized writer wins. There is no optimistic version protocol. Each material override change records `studio.settings_changed`, organization subject/public ID, actor, UTC time, changed override before/after and effective before/after values in the SAME transaction. No-op patches add no audit. Reads are silent. Null reset provenance and actual effective values are retained. Append-only audit constraints remain unchanged. Policy rows contain no customer data.

## Enforcement and historical evidence

Reservation and cancellation writes use the organization then session locks. Policy is current at that transaction's serialization point. The member list/detail response derives can_reserve/can_join_waiting/can_cancel from the same resolver, once per list. Client flags are hints; a stale client request is rejected with localized 409 `policy`. Waiting cancellation retains the prior ability to leave after start, subject to the self-cancellation toggle; confirmed reservation cancellation retains attendance protection and future-start requirements. Repeated already-cancelled requests retain idempotency while cancellation is enabled. Disabling new queue admission neither clears nor reorders an existing queue. Automatic permanent-place allocations and FIFO promotion retain their existing contracts.

QR redemption checks current enablement/windows under the organization/session locks, plus all existing authentication, membership, active reservation, crypto, tenant/session binding and attendance invariants. Old credentials may remain valid until their signed expiry (never over 90 seconds), but must satisfy the current enablement/window. Changing TTL/rotation affects new issuance only. The existing internal legacy attendance adapter retains its previous inclusive late-boundary behavior; HTTP QR uses the exclusive boundary. Staff manual attendance retains its independent fixed 30-minute early window and correction permissions.

Reminder discovery uses a policy snapshot only to bound candidate selection. Each candidate then locks the organization and rechecks the current policy/time range before creating evidence. A setting change can leave newly eligible candidates for the next run; it cannot create an out-of-policy candidate after that change. Disabling optional reminders also suppresses pending deliveries, with current policy checked during claim and completion. Already delivered evidence remains immutable; the inbox can mark it non-current. Lead changes do not alter event keys: type + source/session occurrence identity still prevents duplicates. Suppressed notices are not resurrected on re-enable. Mandatory lifecycle notifications, fixed catch-up/batch limits, delivery retries and recipient preferences remain unchanged. No scheduler/metrics platform is added.

Settings never rewrite sessions, reservations, attendance, sold membership prices/duration/dates, payments, reversals or notification history. Membership expiring-days is read-time presentation, not entitlement or a sold snapshot. Policy acceptance is an instantaneous authorization decision, not a future promise: audit effective before/after values explain the policy at the recorded action time; existing immutable commercial/session snapshots remain authoritative.

## Clients and operations

The web settings page groups General, Reservations, Attendance & Check-In, Notifications/membership display and Member App. Bounded controls show default/override provenance, explicit reset and a confirmation before applying changes. Inputs are read-only without organizations.manage. Native booking/cancellation continues to consume server action flags; the QR screen fetches own settings, fails closed while unavailable, refreshes on focus/app activity and offers manual refresh. The server handles changes occurring after a read. The member web portal consumes the same session flags. Native admin settings are absent.

The additive migration creates only studio_settings; it backfills no defaults and changes no grants. Back up before applying and compare prior-table digests. Rollback drops only the override table, restoring default operational behavior; review rollback impact because audit evidence remains. No cache flush is required. Inspect settings through authorized APIs; do not log settings request bodies or credentials. Usual audit and notification command counts supply operational evidence.

Intentionally NOT configurable: authentication/tenant ownership, staff permissions, capacity/FIFO/active uniqueness, attendance correction authority, reservation/present-attendance protections, QR crypto/binding/hard 90-second maximum, input size/type guards, immutable audit/financial history, scheduler batch limits, arbitrary cron, push providers, currency/payment mechanisms, translations, secrets or signing keys. Deployment, native physical-device proof, production providers and release hardening remain separate work.
