## GHSA-86w9-cpqp-85rv — node-forge

**Installed:** 1.4.0 in GT-016 and GT-017. **Affected:** `<=1.4.0`. **Latest published:** 1.4.0; patched versions: none. Severity high. The nested ASN.1 DigestAlgorithm element-count gap affects RSA PKCS#1 v1.5 signature verification; it is an incomplete fix of an earlier issue. [Advisory](https://github.com/advisories/GHSA-86w9-cpqp-85rv), [disclosure #1149](https://github.com/digitalbazaar/forge/issues/1149), [proposed fix #1152, still open](https://github.com/digitalbazaar/forge/pull/1152).

Terminal dependency paths, with every prefix/context in the appendix:

- `apps/mobile → expo@57.0.28 → @expo/cli@57.0.29 → node-forge@1.4.0`.
- `apps/mobile → expo@57.0.28 → @expo/cli@57.0.29 → @expo/code-signing-certificates@0.0.6 → node-forge@1.4.0`.
- Other Expo packages and `jest-expo@57.0.6` reach `expo` through their dependencies/peers. Root `react-i18next@17.0.14` has an installed React Native peer path into that graph; this does not ship Expo CLI into the web bundle.

GT-016 uses `expo@57.0.26`, CLI 57.0.27 and `jest-expo@57.0.5`; the same two vulnerable terminal paths already exist. GT-017 updates compatible Expo patches and adds direct `expo-file-system@57.0.7` (already transitively present in baseline) and `expo-sharing@57.0.23`. Sharing introduces a new peer route back to Expo, not a new verification feature in app code. Both roots and changed edges are recorded exactly in the appendix.

**Execution/source/control/sink:** installed `@expo/cli/build/src/utils/codesigning.js:182–209` accepts a development-manifest `expo-expect-signature` HTTP header. It selects Expo-root or project signing; this header is untrusted even on a developer network. Project certificates/private keys come from developer configuration/files (`getProjectCodeSigningCertificateAsync`, lines 256–315), not the header. `@expo/code-signing-certificates/build/main.js:176` calls `certificate.verify(certificate)`; lines 200–203 sign a locally generated digest and then call `certificate.publicKey.verify`. Its CSR helper at line 246 also verifies a CSR, but the inspected CLI generates its CSR locally rather than accepting an application-uploaded CSR. The vulnerable implementation is installed `node-forge/lib/rsa.js` plus ASN.1 validation in `lib/asn1.js`; the attack needs a crafted signature/encoded digest reaching verification with a suitable key, not merely attacker-chosen message text.

`apps/mobile/app.json` configures neither `updates.codeSigningCertificate` nor an EAS `extra.eas.projectId`. With those verified settings, project signing returns null without reading a certificate and Expo-root development signing returns null without requesting/caching certificates. Thus a remote manifest header alone cannot reach the signature-verification sink in this configuration. If signing is enabled, local certificates, Expo API/cache responses and keys become security-sensitive inputs; this assessment has **not** validated their complete trust chain or adversarial low-exponent certificates. CLI `run/ios/codeSigning/Security.js:70` parses a PEM from the macOS `security` tool to read identity fields; that inspected path does not call RSA verification. macOS signing itself was not executed here.

**Verified exposure:** development-server/build/signing tooling; absent from inspected backend, web and native application runtime. No demonstrated application-attacker path under current no-signing configuration. **Residual uncertainty:** future EAS/code-signing configuration, plugins, altered local cache/files, macOS signing environments, and supply-chain compromise are not proven unreachable. This is not a finding that the library is fixed.

**Remedy evaluation:** latest CLI 57.0.29 still declares `node-forge ^1.3.3`; latest certificate helper 0.0.7 still declares `^1.4.0`, so updating it does not fix the advisory. Removing Expo CLI breaks required native export/prebuild/start capabilities. Substituting a different crypto library is not a supported drop-in remedy. An unreleased crypto PR/fork or invented 1.4.1 is not applied. Retain the gate until an upstream patched release or reviewed upstream parent replacement is available. Default mobile start is now explicitly loopback; intentional device LAN use remains available via `pnpm --dir apps/mobile exec expo start --lan` on a trusted development network. This reduces network exposure; it does not patch RSA verification.

**Static triage:** `needs_review`, high confidence in installed vulnerability and the current configuration guard, unresolved exploitability outside that configuration. Validation priority 1 among residuals because changing signing configuration would cross a cryptographic trust boundary.

## GHSA-vfj7-8cjw-p6xm — braces

**Installed:** 3.0.3 in both lockfiles. **Affected:** `<=3.0.3`. **Latest published:** 3.0.3; patched versions: none. Severity high. Recursive compile/expand tree walking lacks a nesting bound; deeply nested patterns below the character-length bound can exhaust the JavaScript stack. [Advisory](https://github.com/advisories/GHSA-vfj7-8cjw-p6xm), [open upstream #70](https://github.com/micromatch/braces/issues/70), [compile walker](https://github.com/micromatch/braces/blob/3.0.3/lib/compile.js), [expand walker](https://github.com/micromatch/braces/blob/3.0.3/lib/expand.js).

Every terminal path is `micromatch@4.0.8 → braces@3.0.3`. Every direct micromatch parent present in the actual lockfile is:

- `@jest/core@29.7.0`, `@jest/transform@29.7.0`, `jest-config@29.7.0`, `jest-haste-map@29.7.0`, `jest-message-util@29.7.0`.
- `metro-file-map@0.84.5` and `metro-file-map@0.84.6`.

Prefixes originate in native Jest/React Native/Expo and their installed peers; the appendix includes every nested route, including root React i18next's optional native peer. Baseline already has Jest 29.7.0, micromatch 4.0.8, braces 3.0.3 and Metro; Both Metro file-map versions already occur in GT-016; GT-017 changes Expo parent versions without introducing a new vulnerable file-map version. New Sharing/direct FileSystem importer paths do not introduce user-defined glob features.

**Execution/source/control/sink:** `micromatch/index.js:424–465` passes pattern strings into braces only through `parse`, `braces` and `braceExpand`. The ordinary matching APIs (`micromatch(...)`, `some`, `any`, `matcher`, `makeRe`, `scan`) use picomatch instead. Inspected direct consumers: Jest SearchSource line 358 matches CLI/test paths; transform `shouldInstrument.js:107` uses `any` for coverage patterns; config normalize line 1140 matches configured patterns; haste-map watchers `common.js:61`/FSEventsWatcher line 202 and Metro watchers `common.js:25–27` use ordinary matching; jest-message-util line 318 matches stack filenames against `testMatch`. None of those inspected calls invokes the vulnerable braces walkers. The module may still load eagerly via micromatch's import.

Glob patterns originate in committed Jest/Metro defaults, developer CLI/config and file-watcher setup. Filesystem paths are matching candidates, **not automatically pattern input**. Studio names, report filter values and report data have no flow into those Node configuration APIs. Filename control alone on the inspected matching paths therefore does not establish this specific braces vulnerability. A contributor who can change tooling/config or invoke `micromatch.parse`/`braceExpand` with deeply nested input can reach the installed vulnerable function; character limits and expansion limits do not substitute for a recursion-depth guard.

**Verified exposure:** installed development server/file watching/build and native test tooling; absent from inspected production application bundles/backend. The specific walker is not reachable through the inspected ordinary matching calls. **Uncertainty:** exhaustive execution tracing of every dynamically loaded plugin/alternate CLI command and every future configuration is not performed; supply-chain/workspace contributors remain a tooling trust boundary. Do not describe this as universally unreachable or benign because it is transitive.

**Remedy evaluation:** micromatch 4.0.8 is still latest and requires braces `^3.0.3`. A blanket alias to picomatch changes exported APIs/brace expansion semantics; removing Jest/Metro removes mandatory verification/build capabilities. Arbitrarily pinning an older affected release or adding an unreviewed local walker rewrite does not satisfy this audit. Prefer a released depth-bounded braces fix or supported parent migration; retest brace expansion, watch/test selection and both native bundles when available. Loopback development serving is a bounded mitigation, not an audit resolution.

**Static triage:** `needs_review`, high confidence in installed vulnerability, medium confidence beyond inspected call paths. Validation priority 2; remaining question is whether any supported dynamic tooling entry point supplies attacker-controlled patterns to the walker.

## GHSA-hp3w-g68c-fv3c — sprintf-js

**Installed: 1.0.3**, in both baseline and current lockfile. The earlier completion narrative confused this with **latest published 1.1.3**; it is corrected. **Affected:** `<=1.1.3`; patched versions: none. Moderate severity. Numeric format precision is passed unchecked to `toExponential`, `toFixed` or `toPrecision`, causing a RangeError on oversized precision. [Advisory](https://github.com/advisories/GHSA-hp3w-g68c-fv3c), [disclosure #237](https://github.com/alexei/sprintf.js/issues/237), [open fix PR #239](https://github.com/alexei/sprintf.js/pull/239).

Every terminal path is:

`babel-plugin-istanbul@6.1.1 → @istanbuljs/load-nyc-config@1.1.0 → js-yaml@3.15.2 → argparse@1.0.10 → sprintf-js@1.0.3`.

Native `babel-jest@29.7.0` and `@jest/transform@29.7.0` supply all Babel-plugin prefixes; every Jest/Expo/React Native/optional-peer route is in the appendix. This terminal chain and all target versions are unchanged from GT-016. GT-017 adds Sharing/FileSystem importer/Expo patch routes into the same test-tool graph; it does not add application printf formatting. The new shared report formatter uses Intl and BigInt, not sprintf.

**Execution/source/control/sink:** installed `sprintf-js/src/sprintf.js:76–82` takes precision from the **format string**, not an ordinary substitution value. `argparse/lib/help/formatter.js:325,559,744` uses developer-defined usage/description/help templates; `argument_parser.js:433,445` uses a fixed error template and passes CLI text as an argument. `js-yaml/bin/js-yaml.js` imports argparse for its standalone CLI with fixed option/help descriptions. In contrast, `@istanbuljs/load-nyc-config/index.js:84` calls `require('js-yaml').load(...)` for local YAML configuration. `js-yaml/index.js → lib/js-yaml.js` does not load the CLI or argparse. YAML document contents do not become printf templates along this library path. Installed sprintf is therefore **not reached under this verified NYC library invocation**. Report/member text and financial values never enter these tooling templates.

**Verified exposure:** dependency installed for native coverage/test tooling; a developer can separately invoke the installed js-yaml CLI. It is absent from inspected production bundles/backend and not imported by the inspected NYC YAML library call. **Uncertainty:** arbitrary consumers importing argparse directly, modified help templates and future CLI/plugin usage have not been proven safe. Controlled format strings, not a global input-size assumption, break the inspected application-to-sink path.

**Remedy evaluation:** upgrading sprintf 1.0.3 to latest 1.1.3 remains affected. Latest `@istanbuljs/load-nyc-config` remains 1.1.0 with `js-yaml ^3.13.1`; even latest babel-plugin-istanbul 8.0.0 still depends on that loader. New js-yaml major releases use argparse 2 without sprintf, but overriding the loader's declared major or argparse 1 with argparse 2 is not a compatible upstream parent release: parser/schema and CLI APIs differ. No project need justifies assuming all supported NYC configuration semantics survive that substitution. See the [upstream dependency migration request](https://github.com/istanbuljs/load-nyc-config/issues/26). Removing instrumentation/Jest to erase the path would remove required capabilities. Selectively deleting argparse/sprintf from js-yaml’s declared dependencies would leave its shipped CLI broken; non-use by the inspected NYC library entry point does not establish that this is a supported unused-package removal. A supported upstream separation or migration is preferable to that broken manifest. Wait for a supported loader/parser migration or upstream precision fix; do not delete a required transitive dependency by hand.

**Static triage:** `not_actionable` for the inspected application/NYC-library threat path, high confidence in that limited conclusion; the vulnerable installed package remains an audit finding and therefore remains in the gate/exception proposal. No claim of package remediation or universal CLI safety is made.
