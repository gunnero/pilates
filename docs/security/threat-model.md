# GT foundation threat model

## Overview

GT is a Laravel/React modular monolith with identities, organization/location/staff and client lifecycles and a localized management shell. Browser → Laravel session/Sanctum → explicit membership/permission checks → PostgreSQL is the current data path. User-provided scope is HP local development only, no public deployment, customer self-access or payment modules. GT-007 adds staff-managed booking as described below. This model incorporates an independent read-only architecture review; final source anchors and later fixes were checked by the implementing agent. Scenarios below are hypotheses/design risks, not confirmed vulnerabilities.

## Threat Model, Trust Boundaries, and Assumptions

Assets are account/session/token authority, organization metadata and access grants, location ownership, staff lifecycle and audit integrity, future financial/attendance integrity, private credentials, and service availability. An unauthenticated caller that can reach loopback (or a future exposed deployment) can choose headers, body and routes. An authenticated staff user can guess other organizations' UUIDs and attempt higher-privilege actions. A token holder has only their existing user identity/abilities. A malicious website can attempt CSRF. None is assumed to control the HP account, source dependencies, private configuration, DB administrator or shared Redis administration.

The user-to-organization boundary is enforced by an active membership/organization join followed by permission evaluation. Missing membership returns 404; a known member without studio.access receives 403. Context clears on resolution and after requests. The identity bootstrap `/me` intentionally returns the user's own organization choices, without an extra token ability requirement. Financial permission names do not imply one another. Role/grant writes require staff.manage and permissions.manage plus bounded delegation; owner custody adds a restriction. No global Super Admin or Owner permission bypass exists.

The browser boundary uses CSRF, encrypted HttpOnly sessions, same-origin fetch, escaped React text, bounded JSON errors and response security headers. Local HTTP is a deliberate exception to Secure cookies; APP_ENV=production forces Secure, HSTS and debug=false. These settings alone do not establish safe production hosting. In production sessions must remain database backed on the same DB connection for atomic credential revocation. The review's original hardcoded-table caveat was fixed by honoring session table/connection configuration.

PostgreSQL is authoritative; Redis loss must not alter business entitlements or payments. Shared-host processes with unrestricted Redis access can affect cache/limits; GT prefixes do not isolate adversarial apps. Runtime DB roles own schemas locally for migrations; production must separate DDL/runtime/audit-retention authority. No automatic tenant global scope or RLS exists. Future routes/jobs/exports require their own explicit scoped queries and tests.

Customer self-access/booking/payment modules, real outbound email, mobile token issuance, MFA, off-host immutable audit export, production backups and public hosting are absent. Lifecycle audit DML is now append-only; schema administrators can still alter it. Recovery notification translation/transport and timing behavior need review when real mail is enabled. Framework job failure payloads require redaction before adding jobs. This model does not certify the host, vendor implementations or supply chain.

## GT-002 lifecycle trust boundaries

The organization UUID in a route is an untrusted selector. Active membership, active organization and studio.access establish context; the operation Gate establishes authority. The session's selected organization is a preference only. Token abilities are intersected at every gate. `/me` exposes only the caller's active accessible organization choices, but does not itself require an extra token ability.

Locations are constrained by organization and all/selected assignments, with composite foreign keys preventing cross-tenant links. `staff.view` intentionally reveals the organization-wide staff directory even for a selected-location actor; permissions and assignment IDs have separate serialization checks. This is a documented disclosure policy, not branch-directory isolation. GT-003 now holds customer PII in StudioMember, protected by a stricter all-location client boundary below.

Supported mutations lock the organization row, re-resolve actor authority and persist change/evidence atomically. This prevents stale grants and concurrent last-owner removals in those paths. Aggregate owner count is not protected from trusted raw SQL. Revoked memberships are terminal in the lifecycle service and retained. Already-running reads can finish on their request snapshot. Future jobs must establish context and follow the lock protocol.

| Scenario                                            | Control / tested evidence                                                                 | Remaining assumption                                |
| --------------------------------------------------- | ----------------------------------------------------------------------------------------- | --------------------------------------------------- |
| Both owners concurrently remove themselves          | Three real PostgreSQL contention tests: revoke, suspend, demote; one success/one conflict | All writers use the common organization lock        |
| Delegated manager promotes/grants beyond authority  | Existing/proposed grants subset of actor effective permissions; owners need owner custody | Operator/DDL access is trusted                      |
| Selected-location actor accesses a different branch | Context location predicate before lookup/list/write, scoped delegation and composite FKs  | New aggregates must reuse scope enforcement         |
| Actor erases audit or audit failure hides mutation  | UPDATE/DELETE/TRUNCATE triggers, failure rolls back transaction                           | Local schema owner can disable triggers/drop tables |
| Browser remembers revoked tenant selection          | Fresh context on every request, post-lock recheck, `/me` validates preference             | In-flight reads are not retroactively canceled      |

`gt:organization-create`, `gt:organization-status` and `gt:owner-bootstrap` are trusted host capabilities, with system actor audit evidence and no password creation. Bootstrap refuses an existing active owner and revoked target membership. These commands are not public API administration and do not add a blanket Gate bypass.

The audit byte cap is 8192 with allowlisted shallow structures. Request correlation IDs, retention/export and audit viewer authority remain deferred. See [lifecycle](../architecture/organization-lifecycle.md), [audit](audit.md) and [focused review](gt-002-review.md). The independent review found no validated supported-path boundary bypass; implementation review fixes are recorded with verification in those documents.

## Severity Calibration (Critical, High, Medium, Low)

**Critical:** unauthenticated remote access that reliably yields platform-wide secrets or all-tenant authority in an actually exposed deployment. A loopback listener or an already-authorized HP operator reading their own files is not this case. No such finding is established.

**High:** authenticated cross-tenant reads/writes, unauthorized payment correction, or practical account takeover. Current context/Gate/reset controls are counterevidence; a future unscoped route or real-mail weakness must be demonstrated before calling it a finding.

**Medium:** exploitable limited resource exhaustion, scoped information exposure, or unsafe deployment configuration with a concrete reachable prerequisite. Native shared Redis trust is an operational boundary limitation; its existence alone does not prove a remote attack.

**Low:** bounded non-sensitive disclosure or defense-in-depth gaps with little added authority. A visible Coming soon payment link does not disclose financial data. Unsupported booking/payment scenarios remain future design obligations, not vulnerabilities in absent code.

Impact and confidence are separate. Browser/feature tests support specific controls, not exhaustive assurance. Revisit this model when public hosting, tenant aggregates, sensitive writes, jobs, actual mail or mobile token issuance are introduced.

## GT-003 customer PII boundary

StudioMember is an organization-owned customer identity, with optional contact details/operational notes and optional future User linkage. It is never staff authority or a purchased package. New assets include customer names/contact/notes and profile history. No customer mobile/self-service endpoint exists.

The client surface is `/api/v1/organizations/{UUID}/members` plus JSON POST search and dedicated status mutation. MemberDirectory requires active tenant/staff context, members.view and **all-location scope** before query/representation. Selected-location actors are denied regardless of role/grants/home-location match, until real group/session relationships can support a narrower rule. Per-operation create/update/status permissions and independent notes view/manage capabilities apply. Token abilities remain intersected.

| Attacker story                                                    | Mitigation and evidence                                                                        | Residual boundary                                                            |
| ----------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| Trainer enumerates organization clients using known home location | No selected-location client access; Trainer default has no client permission; API tests        | Future sessions must define actual relevance before relaxing visibility      |
| Staff guesses another tenant member UUID or preferred location    | Scoped queries, 404s and composite preferred-location FK, tested on PostgreSQL                 | Trusted raw SQL/DDL remains outside application guarantees                   |
| Profile viewer extracts notes from list or response               | Notes omitted from list SELECT and all responses without notes.view; separate write Gate       | Authorized note viewers can read entered operational text                    |
| PII escapes via search URLs, audit or exception logs              | JSON body prefix search, minimized audit metadata, class-only errors; regression tests         | Production proxy/body telemetry and backups need access/redaction policy     |
| Customer User link becomes staff access                           | Nullable linkage is API-immutable; authorization still requires OrganizationMembership; tested | Future claim process must verify identity without contact-only auto-linking  |
| Archived client edited/reactivated without deliberate recovery    | Profile edit 409; archived → inactive restore before active; no delete                         | Archived detail remains visible to authorized staff, not an erasure workflow |

Duplicate warning is tenant-scoped and advisory, not contact ownership proof or global identity lookup. Notes are bounded operational text, not structured medical records. Field encryption, retention/export/deletion, staff misuse controls and customer consent need future product/deployment decisions. Direct PII values are not duplicated into audit, but audit member UUIDs still identify the referenced record and require protection. GT-003 does not claim a legal compliance outcome. See [review](gt-003-review.md) and [domain/privacy decisions](../domain/studio-members.md).

## GT-004 operational trainer boundary

TrainerProfile is an optional operational record attached to one staff membership, never authentication or a grant source. New assets are teaching display name/bio and assignment-eligibility information. There is no public/member-facing trainer endpoint. Existing organization/staff authority remains the only entry into this domain.

## GT-006 session boundaries

Attackers may guess session/group/trainer UUIDs, forge source identity or timestamps, request huge calendars, race generation/cancellation/overrides, or exploit stale teaching eligibility. Sessions apply current tenant/location/grant checks and own-trainer restrictions, strict input allowlists, fixed generation/bounded calendar horizons, composite FKs, unique source/date identity and native concrete-time exclusions. Shared organization locking couples authorization, current eligibility, mutation, reconciliation and append-only audit. Cancelled identities and explicit override markers resist automated resurrection/rewrite. Reconciliation fails as a whole on protected exceptions or inaccessible affected rows. Fixed-code conflict responses expose no conflicting object details. Snapshot names/reasons are escaped operational staff data; no member relationship exists. Trusted CLI and schema-owner access remain privileged boundaries. Current limits include no host scheduler, conservative exception handling, request-scoped already-running reads and per-group synchronous generation.

## GT-007 allocation and customer schedule privacy

Reservation identities and member/session relationships are customer operational assets. Threats include final-place races, malicious capacity reduction, queue jumping, duplicate permanent assignment, exception loss, cross-tenant injection and cross-location member enumeration. Organization locking couples fresh staff authority to session-row locking and active-count allocation; group admission sweeps inclusive future effective periods under the same lock. Native partial indexes protect active uniqueness, GiST excludes duplicate permanent periods, and composite FKs protect tenant parents. Cancellation and FIFO promotion share one transaction. Durable release rows prevent synchronization replay from restoring a deliberately released place.

Explicit reservation/waiting/permanent grants are independent of profile and financial authority. Session lookup exposes at most 20 public IDs/names only inside an authorized workflow; general member-directory restrictions remain. Prefix input is bound and escaped, representations omit contacts/notes, and React escapes display text. Routine logs contain identifiers/counts, audit is bounded and transactional. Tests include twelve real competing-process scenarios plus privacy/negative API tests. Aggregate capacity and cross-table exclusivity remain supported-service invariants, not raw-SQL CHECKs; schema owners remain trusted. Authorized staff can intentionally misuse their permitted lookup, so production access review, retention and monitoring remain operational obligations. No member-authentication adapter or notification delivery exists.

## GT-008 attendance extension

GT-008 now implements durable attendance, staff/trainer roster and today workflows, capacity-safe offline walk-ins, no-show finalization, audited corrections and encrypted expiring QR foundations. Earlier attendance deferrals above describe the prior milestone. See [attendance contracts](../domain/attendance.md) for authorization, API, privacy, concurrency, lifecycle protection and future member-authentication boundaries. Existing grants are preserved; adoption is explicit. No member check-in HTTP endpoint, payments, mobile app or GT-009 is included.

Attendance-specific assets are member/session presence history, correction evidence and QR challenges. Staff UUID selectors cross the tenant and location/assigned-trainer boundary; TenantContext, SessionDirectory and post-lock Gates protect both reads and writes. A forged member UUID never substitutes for authenticated member identity: the future internal adapter derives StudioMember from the authenticated User and has no public route. A leaked QR challenge alone conveys no reservation or member identity; Crypt integrity, session binding and a maximum 90-second expiry restrict use, while short-window replay by eligible members remains an explicit design property. QR payloads stay out of URLs, logs, audit, external services and persistent browser storage.

Attendance and cancellation share organization serialization; present records prevent ordinary reservation cancellation, and any attendance protects session changes/cancellation. Walk-in uses the existing active-count allocator and FIFO promotion, with booking/attendance/audit rollback together. No-show finalization is bounded to one tenant, 31 dates and 200 sessions and never overwrites resolved attendance. Audit actor/status/method/time/reason-code history is bounded and append-only. Trusted DB administrators can bypass service-level cross-table invariants; the read-only checker detects invalid combinations. Future public mobile authentication/linking, edge telemetry and exceptional cancellation policies require new review rather than inheriting staff or QR authority.

## GT-009 financial trust boundary

Assets now include agreed commercial snapshots, immutable cash/reversal evidence and balances. Untrusted requests cannot choose tenant, actor, currency or internal associations. Risks reviewed: cross-tenant IDOR, financial serialization, trainer/location grant confusion, forged actors/source, duplicate retries/reversals, conflicting membership periods, stale authority, audit failure and arithmetic read-skew. Mitigations are explicit gates/resources, organization-lock reauthorization, tenant-qualified FKs, append-only triggers, one reversal constraint, overlap exclusion and single-statement aggregate snapshots. Notes remain bounded and absent from audit/list URLs. Database-owner bypass and physical cash truth remain outside HTTP guarantees. See [GT-009 review](gt-009-review.md).

## GT-010 notifications

GT-010 adds private recipient inboxes, event snapshots, read state and durable delivery leases. Threats include cross-recipient/tenant UUID access, forged member identity, unsafe source relationships, replay, stale source delivery, financial leakage, duplicate scheduler/worker races and retry storms. Controls: authenticated User-derived recipients, current TenantContext staff gates/scope, organization-lock rechecks, concrete composite FKs, bounded registry metadata, immutable evidence, unique event/delivery keys, leased attempts and bounded exponential retry. Payloads omit all monetary values and customer contact/notes. Delivery rechecks sources before publication; historical delivered evidence is retained. Provider-neutral interfaces do not claim external exactly-once semantics; future adapters require provider idempotency. Database owners, account linking, retention and external push credentials remain trusted/deferred boundaries. See [notifications](../domain/notifications.md) and [GT-010 review](gt-010-review.md).
