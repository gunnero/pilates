# GT foundation threat model

## Overview

GT is a Laravel/React modular monolith with identities, organization access and a localized studio shell. Browser → Laravel session/Sanctum → explicit membership/permission checks → PostgreSQL is the current data path. User-provided scope is HP local development only, no public deployment or business modules. This model incorporates an independent read-only architecture review; final source anchors and later fixes were checked by the implementing agent. Scenarios below are hypotheses/design risks, not confirmed vulnerabilities.

## Threat Model, Trust Boundaries, and Assumptions

Assets are account/session/token authority, organization metadata and access grants, future financial/attendance integrity, private credentials, and service availability. An unauthenticated caller that can reach loopback (or a future exposed deployment) can choose headers, body and routes. An authenticated staff user can guess other organizations' UUIDs and attempt higher-privilege actions. A token holder has only their existing user identity/abilities. A malicious website can attempt CSRF. None is assumed to control the HP account, source dependencies, private configuration, DB administrator or shared Redis administration.

The user-to-organization boundary is enforced by a membership join followed by permission evaluation. Missing membership returns 404; a known member without studio.access receives 403. Context clears on resolution and after requests. The identity bootstrap `/me` intentionally returns the user's own organization choices, without an extra token ability requirement. Financial permission names do not imply one another. No public role/grant writes or global Super Admin bypass exist.

The browser boundary uses CSRF, encrypted HttpOnly sessions, same-origin fetch, escaped React text, bounded JSON errors and response security headers. Local HTTP is a deliberate exception to Secure cookies; APP_ENV=production forces Secure, HSTS and debug=false. These settings alone do not establish safe production hosting. In production sessions must remain database backed on the same DB connection for atomic credential revocation. The review's original hardcoded-table caveat was fixed by honoring session table/connection configuration.

PostgreSQL is authoritative; Redis loss must not alter business entitlements or payments. Shared-host processes with unrestricted Redis access can affect cache/limits; GT prefixes do not isolate adversarial apps. Runtime DB roles own schemas locally for migrations; production must separate DDL/runtime/audit-retention authority. No automatic tenant global scope or RLS exists. Future routes/jobs/exports require their own explicit scoped queries and tests.

Business write modules, real outbound email, mobile token issuance, MFA, immutable audit storage, production backups and public hosting are absent. Recovery notification translation/transport and timing behavior need review when real mail is enabled. Framework job failure payloads require redaction before adding jobs. This model does not certify the host, vendor implementations or supply chain.

## Severity Calibration (Critical, High, Medium, Low)

**Critical:** unauthenticated remote access that reliably yields platform-wide secrets or all-tenant authority in an actually exposed deployment. A loopback listener or an already-authorized HP operator reading their own files is not this case. No such finding is established.

**High:** authenticated cross-tenant reads/writes, unauthorized payment correction, or practical account takeover. Current context/Gate/reset controls are counterevidence; a future unscoped route or real-mail weakness must be demonstrated before calling it a finding.

**Medium:** exploitable limited resource exhaustion, scoped information exposure, or unsafe deployment configuration with a concrete reachable prerequisite. Native shared Redis trust is an operational boundary limitation; its existence alone does not prove a remote attack.

**Low:** bounded non-sensitive disclosure or defense-in-depth gaps with little added authority. A visible Coming soon payment link does not disclose financial data. Unsupported booking/payment scenarios remain future design obligations, not vulnerabilities in absent code.

Impact and confidence are separate. Browser/feature tests support specific controls, not exhaustive assurance. Revisit this model when public hosting, tenant aggregates, sensitive writes, jobs, actual mail or mobile token issuance are introduced.
