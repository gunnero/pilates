# GT-005 focused implementation review

Reviewed the group/weekly-schedule changes against clean baseline e7487a4154820eadc3ef63b7059123b7afb44dea, following the request's tenant, lifecycle, concurrency, history and audit requirements. This is an implementation source review with automated regression evidence; it is not a separate Codex Security workbench scan or independent penetration test.

## Boundaries inspected

- GroupDirectory, TrainingGroupController, ScheduleRuleController and nested routes constrain tenant/location/group ownership before reading or serializing. Foreign group, location, trainer and rule UUIDs are tested, including a selected manager's inaccessible same-tenant group. No internal IDs, private staff identity/grants or clients appear in group/rule representations. Schedule data is omitted without schedule.view. Trainer filtering checks trainers.view and its scope.
- GroupLifecycle and ScheduleLifecycle re-resolve current actor authority under Lifecycle's common organization lock. Location/trainer changes validate current scope/status; status activation and assignment changes recheck trainer conflicts. A profile never supplies authority. Selected-location client access remains denied even with a visible group.
- Requests reject unknown/protected keys and bound names/descriptions/capacity/pagination/date/time. SQL search uses bound escaped literal prefixes; timing overlap uses bound dates. Profile writes cannot set status, tenant or identity. React renders plain escaped strings and uses the existing same-origin CSRF client. Group navigation is tenant/path-keyed; a location change clears the trainer selection and loads currently eligible choices.
- Migration enforces tenant-qualified location/trainer/group/predecessor FKs, UUID uniqueness, capacity/status/weekday/time/date constraints and non-canceled same-group overlap with native GiST ranges. No privileged extension install is required. Existing grants/data are not rewritten. Legacy upgrade tests still exercise their original schema baseline.
- Cross-group trainer conflicts are protected by the organization-lock supported-writer protocol, not merely an unlocked SELECT. Real PostgreSQL child processes test duplicate, same-group overlapping and cross-group same-trainer writes: only one success and one conflict, one rule/audit event. Inactive groups recheck on activation; active unavailable groups continue reserving conflict intervals to make restoration safe.
- Weekly history has no general time/start-date update or DELETE. Close only shortens a current/future end; replacement atomically closes predecessor and creates successor; cancellation retains a not-yet-started definition. A second replacement of the same predecessor returns 409 rather than surfacing a database uniqueness error. Conflict and audit-failure tests prove predecessor/new-row rollback.
- Group audit evidence records field names and bounded scalar/public references, not name/description values. Rule evidence retains bounded wall-clock/date changes. Append-only audit triggers remain intact. Source trainer/staff/location lifecycle events evidence derived group unavailability without duplicate fan-out state.
- Rule meaning uses the organization's inherited timezone. Settings changes cannot silently reinterpret a rule's local time: timezone edits are rejected once any rule exists. Recurring local time is not serialized as UTC. No dated occurrence or DST resolver is claimed.

No concrete supported-path tenant, permission, serialization, audit or concurrency bypass remained in this review. Implementation tests caught and corrected a typed eager-loading callback incompatible with relation arguments before completion. Browser checks corrected exact-label selectors to use the controls' accessible roles. The expanded back-to-back desktop/mobile flows exceeded one shared fixture account's rate limit, so each viewport now has a separate fixture owner; the real API limiter remains unchanged. No authorization or production invariant was relaxed.

## Explicit limitations

Trusted raw SQL/DDL can bypass application invariants and modify schema/audit controls; production runtime/migration privileges remain a deployment prerequisite. Same-group overlap is database-enforced, while cross-group trainer conflicts depend on all supported writers acquiring the shared organization lock. Already-running reads can complete on their request state. Future session generation must recheck current readiness under lock and snapshot dated values.

Date/time overlap is conservative for short periods with no actual matching weekday. Clock intervals are same-day and at most four hours. All organization locations share one timezone; cross-organization scheduling, travel buffers, rooms and resource exclusivity are not implemented. A location can host simultaneous different-trainer groups. DST exceptions require explicit future occurrence resolution; no silent shift or double generation is permitted by the documented policy.

The group representation intentionally includes the retained trainer's operational name/UUID even if now unavailable, while hiding their staff role/membership/email/grants. An out-of-scope trainer conflict reveals only that a proposed interval conflicts, not the conflicting group's identity. Group/schedule management does not change client visibility or financial access.
