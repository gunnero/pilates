# GT-003 security and privacy review

Focused review of migration, client queries/representations, validation, permissions, lifecycle/audit, operator adoption and React workflows. Source review plus application/PostgreSQL/browser tests; not an exhaustive security scan or penetration test.

| Boundary / risk                             | Controls and verification                                                                                                                                                                                                                         |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Cross-tenant member access / guessed UUID   | Query organization is resolved from active staff membership; all list, detail, update/status and duplicate queries are tenant-scoped. Foreign and random UUID tests return 404.                                                                   |
| Organization spoofing / mass assignment     | Unknown fields rejected; guarded model, explicit validated writes. organization_id, user_id, public/internal IDs, status on profile writes, timestamps and audit fields cannot be submitted.                                                      |
| Location bypass                             | Composite preferred-location FK plus scoped lookup. New inactive assignments reject. All client endpoints require all-location scope, including searches/creates/status. Matching home location does not bypass this.                             |
| Staff escalation / future customer accounts | New permissions are finite, independent and token-intersected. Existing grants unchanged by migration. Optional linked user gains no staff membership/permission; tested.                                                                         |
| Note disclosure                             | Separate view/manage Gates. Directory never selects/serializes notes. Detail selects notes only with notes.view. Notes absent from response for blind authorized writers; UI does not silently clear undisclosed notes.                           |
| Contact enumeration                         | Requires active tenant staff, members.view and all-location scope. Duplicate result is a boolean after an authorized write, includes no candidate PII and is tenant-scoped. Shared contacts allowed.                                              |
| PII in logs/audit/URLs                      | Bound JSON POST search; no query-string search API. Profile/notes values excluded from audit; tests inspect all member metadata. Generic errors/class-only logs tested under injected audit failure. No frontend console/debug/storage additions. |
| Suspended/revoked actors and stale context  | Re-resolve active membership and organization per request and again after mutation lock. Tests cover suspended organization, suspended/revoked staff, and revoke-after-resolution.                                                                |
| Archived handling                           | Default listing excludes archived; explicit history access remains authorized. Profile editing blocked; archived → active rejected; inactive restoration required. No delete endpoint.                                                            |
| API over-serialization                      | Explicit UUID-based member representation, no internal/user/tenant IDs. Notes only on authorized detail; preferred-location details additionally require locations.view. No audit metadata in profile responses.                                  |
| Integrity / atomicity                       | PostgreSQL enum/contact/UUID/FK/optional-link constraints tested. Existing audit tamper triggers still reject update/delete/truncate. Injected audit failure rolls back profile mutation.                                                         |
| Query cost / wildcard search                | Bounded literal prefix search and pages, tenant-leading indexes, eager location query count assertion. No substring/fuzzy or global contact search.                                                                                               |

Review decisions/fixes: deny all selected-location actors until actual attendance relationships exist; preserve legacy permission sets and require explicit audited adoption; avoid duplicate PII in before/after audit; keep notes excluded from list queries and blind-edit forms; do not place contact searches in URLs. Review also tightened the locations.view check to cover clearing a preferred location, preventing a client editor without location visibility from removing an undisclosed preference; a regression assertion covers this. Existing GT-002 role/owner/audit guarantees remain covered by the full regression suite.

Remaining limitations are deliberate: authorized members.view includes contact data; no separate contact-view permission yet. Duplicate matching is advisory/exact, not a merge system. In-flight reads can complete on their request snapshot. There is no RLS or field encryption, and trusted schema/host operators can bypass application rules. Infrastructure request-body logs/telemetry must remain disabled or redacted in a future deployment. Free-text notes require operational policy. Retention/export/deletion, backup retention and verified customer account claims require future designs. See [domain/privacy decisions](../domain/studio-members.md) and the threat model.
